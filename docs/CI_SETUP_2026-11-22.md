## Repository plan and permissions

The authenticated repository API reports `private: true` and administrator
access. Actions is enabled and the Actions public-key endpoint is accessible.
The branch-protection endpoint returned HTTP 403 with this exact message:

> Upgrade to GitHub Pro or make this repository public to enable this feature.

This restriction is the repository's current plan/visibility combination.
GitHub Free supports branch protection for public repositories; private
repositories require an eligible paid plan. See
[protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches).

Choose whether to keep private/Free with review by team agreement, upgrade
while keeping the repository private, or deliberately make the repository
public. A visibility change exposes tracked code and history and requires
an explicit owner decision. CI setup does not change visibility or purchase
a plan.

## Workflow behavior

`.github/workflows/offline-tests.yml` declares PRs targeting `main`, pushes to
`main`, and manual dispatch. The single `offline-regression` job uses standard
`ubuntu-latest` and Python 3.13, with a ten-minute timeout and cancellation of
superseded runs. Official checkout and setup-python v6 actions are pinned to
their resolved commit SHAs. The workflow checks out the PR merge candidate
using the default pull-request event; it does not use `pull_request_target`.

The job restores only the approved FDA starter ZIP, installs pinned project
dependencies, runs `pip check`, and executes the permitted pytest selection
documented in [CONTRIBUTING](../CONTRIBUTING.md). Its job summary identifies
the 21 inventory-dependent tests outside that selection. It creates no cache
or uploaded result artifact and needs no OpenAI or Qdrant credentials.

GitHub-hosted execution, dependency downloads and a fresh Linux environment
remain unverified until the first actual run. Local YAML parsing is not a
substitute for a hosted Actions run.

## Private FDA fixture

Create a repository Actions secret named `FDA_STARTER_ZIP_BASE64`, containing
the base64 encoding of the original ZIP bytes. The current 33,201-byte ZIP
encodes to 44,268 ASCII bytes, below GitHub's 48 KB secret size limit. The ZIP
is neither added to Git nor extracted. See
[Actions secrets](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-secrets).

`scripts/prepare_ci_source.py` reads the secret from its process environment,
verifies SHA-256
`b1f55e7cc2b0ec37c29b87af31478230766b3ba9b45bd0db03c8c38c1bfe2f0e`,
and exclusively creates the source at the expected sibling reference path
with mode `0600`. It accepts an existing identical file without rewriting it
and refuses to overwrite a different file. Missing/invalid input fails the
job clearly before tests, rather than skipping source validation.

The secret is not provisioned yet. Do not post its value in a PR or chat,
print it to CI logs, or substitute inventory/label archives. Only trusted
repository contributors should have access to the workflow and this fixture.
Fork PRs do not receive ordinary Actions secrets and will need a maintainer's
separately reviewed fixture/run arrangement; never change the trigger to
`pull_request_target` to bypass that limitation.

## Activation and merge policy

For private repositories, hosted Actions consumes the account's included
compute allowance and can incur additional charges. Confirm the account's
current allowance and spending controls before publishing/enabling this
workflow. Public repositories have free standard hosted runner compute;
storage and larger-runner rules are separate. See
[Actions billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions).

After the owner chooses a plan/visibility and approves the applicable compute
usage, provision the private fixture, publish the CI branch, and open a PR to
`main`. Inspect the first actual run, including dependency installation and
the exact test selection. A successful run is required before treating the
workflow as operational.

On a plan/visibility that supports protection, configure `main` to require a
pull request, one approving teammate review, conversation resolution and the
successful `offline-regression` check. Keep force pushes and deletion blocked.
Apply the intended rules to maintainers too, rather than silently bypassing
them. A reviewer must use a different account from the PR author.

On private/Free, use the same review process by team agreement and report that
GitHub does not enforce it. Do not claim the branch is protected or that
local test results are a hosted CI check.
